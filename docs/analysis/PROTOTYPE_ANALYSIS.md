# yumidang6 프로토타입 현황 분석

분석일: 2026-09-14 · 기준 커밋: `96da16b7f7f0485c3e8dd14b86f3dc8338e7547f`

## 1. 이번 분석의 기준

사용자 지시: **“우선 프로토타입을 만드는 거라고 생각해.”**

목표는 사용자가 동행을 탐색하고, 신청하고, 상대의 수락을 거쳐 약속·채팅·평가까지 경험할 수 있는 프로토타입의 완성도를 파악하는 것이다. 실제 SMS, 결제, 통화, 다중 사용자 서버 구현 여부를 현재의 완료 조건으로 두지 않는다. 가상 응답은 사용할 수 있지만, 역할·데이터·화면 전환은 같은 시나리오를 따라야 한다.

기능 추가·삭제나 UI 수정은 수행하지 않았다. 아래 개발 순서는 제안이며, 기존 기능의 포함·보류·제외를 새로 확정한 문서가 아니다.

- [`src/main.tsx`](../../src/main.tsx) → [`src/App.tsx`](../../src/App.tsx): 앱 실행, 현재 탭·모달·사용자·공고·신청·약속·후기 상태 관리.

- [`src/components`](../../src/components): 화면과 폼. 채팅 메시지와 평가 진행 단계 등 일부 상태는 개별 컴포넌트에 존재.
- [`src/utils/trackFunnelEvent.ts`](../../src/utils/trackFunnelEvent.ts), [`trackBackEvent.ts`](../../src/utils/trackBackEvent.ts): Supabase로 행동 이벤트 전송 시도.

탭은 URL 라우팅이 아닌 `activeTab` 값으로 전환한다. 모달도 여러 상태값으로 열고 닫는다. 공고와 신청은 배열이지만 확정 약속은 하나의 객체라, 다른 약속을 수락하면 현재 약속을 덮어쓴다.

## 4. 먼저 고칠 흐름 문제

아래 ‘재현’은 로컬 프로덕션 빌드를 브라우저에서 조작한 결과다. 실제 사용자의 행동 관찰 결과는 아니다. Supabase 요청은 가로채어 실제 DB에 테스트 데이터를 쓰지 않았다.

### A. 신청자와 호스트 역할이 섞임 — 우선순위 높음

- **재현:** 비로그인 상태에서 받은 신청함을 열고 샘플 신청을 수락해 약속을 확정할 수 있다.
- **재현:** 로그인한 사용자가 다른 사람의 공고에 신청한 뒤, 같은 사용자의 받은 신청함에서 자기 신청을 수락할 수 있다.
- **코드:** `App.tsx:444–549`, `:774–778`, `:957–963`. 신청함에 전체 `joinRequests`를 넘기며 수락 처리에 호스트 조건이 없다.
- **샘플 불일치:** 최초 신청 2건의 `postId`는 `m4`지만, 공고 ID는 `post-1`~`post-7`이다. 수락 시 실제 공고를 찾지 못하고 대체 제목·장소·날짜 흐름에 의존한다.
- **영향:** ‘상대가 검토하고 수락했다’는 서비스의 핵심 경험을 시연하기 어렵다.
- **제안:** 고정된 체험 사용자 2명과 연결된 공고·신청 데이터를 사용하고, 역할별로 보낸 신청과 받은 신청을 나눈다. 실제 서버 없이도 구현할 수 있다.

### B. 이동하면 진행 내용이 사라짐 — 우선순위 높음

- **재현:** 채팅 메시지 전송 → 홈 → 채팅으로 돌아오면 방금 보낸 메시지와 자동 답장이 사라진다.
- **재현:** 가상 로그인 → 공고 작성 → 새로고침하면 로그인 상태와 공고가 초기화된다.
- **재현:** 비회원이 모집 버튼 → 로그인 완료까지 진행해도 모집 폼으로 이어지지 않아 다시 눌러야 한다.
- **코드:** `ChatView.tsx:32–51`, `App.tsx:301–309`, `:325–331`, `:671–683`, `:845–858`.
- **제안:** 채팅·공고·신청·약속을 함께 유지하는 공통 상태를 만들고 로그인 후 원래 작업으로 복귀한다. 새로고침까지 유지할지는 테스트 방식에 맞춰 정하되, 초기화는 명시적으로 할 수 있어야 한다.

### C. 한 번의 평가가 두 번 정산됨 — 우선순위 높음

- **재현:** 평가 제출 → ‘상대방 제출 즉시 시뮬레이션’ 클릭 → 자동 처리 타이머까지 기다리면 당도가 **50 → 54**가 된다. 의도된 한 번의 +2 정산이 두 번 호출된다.
- **코드:** `ReviewModal.tsx:49–82`, `:278–285`, `App.tsx:636–668`.
- **추가 확인:** 완료 후 마이페이지에도 ‘진행 예정 동행 (1건)’이라는 고정 문구가 남는다.
- **제안:** 약속별 평가·정산 완료 상태를 하나로 관리하고 중복 실행을 막는다. 시연 버튼과 자동 응답이 같은 완료 규칙을 사용하도록 한다.

### D. 상세 장소 공개 조건이 시나리오와 다름 — 우선순위 높음

- **재현:** 비로그인 상태에서 마감된 브런치 공고를 열면 ‘매칭 확정자 전용 상세 장소’와 예약석 정보가 보인다.
- **코드:** `PostDetailModal.tsx:43–47`, `:195–203`. `isHost || isClosed`를 공개 조건으로 사용하고, 작성자 판정에는 마스킹된 이름 비교도 포함된다.
- **영향:** ‘확정된 나와 상대만 상세 장소를 볼 수 있다’는 신뢰 장치의 시연이 잘못된다. 현재 데이터는 샘플이며, 실제 개인정보 유출을 확인한 것은 아니다.
- **제안:** 체험 사용자 ID와 해당 약속의 참여자 ID로 공개 여부를 결정한다. 이름과 모집 마감 여부를 참여 자격 대신 사용하지 않는다.

## 6. 유지보수와 문서

1. **`App.tsx`에 여러 책임이 모여 있다.** 화면 전환, 상태 변경, 샘플 데이터, 이벤트 기록이 함께 있어 한 흐름의 수정이 다른 흐름에 영향을 주기 쉽다. 기능별 상태/동작을 분리하고, 공통 모달·버튼·화면 너비부터 재사용하는 정도의 정리가 적절하다.
2. **TypeScript 검사 통과의 범위가 제한된다.** `@types/react`, `@types/react-dom`이 설치되어 있지 않고 엄격 모드도 켜져 있지 않다. 예를 들어 일반 수락 시 생성하는 약속 객체는 `Appointment`의 여러 필수 필드와 맞지 않지만 현재 검사를 통과한다. React 타입 정의를 갖춘 뒤 실제 오류를 확인할 필요가 있다. [React 공식 TypeScript 안내](https://react.dev/learn/typescript)
3. **문서의 완료 기준이 혼재한다.** `ROADMAP.md`는 자동 만료·단일 확정 트랜잭션 등을 완료로 표시하지만, 코드에서는 시뮬레이션이거나 해당 처리가 없다. `MVP_USER_FLOW_CHECKLIST.md`는 이메일 OTP를 설명하지만 현재 인증 폼은 휴대폰 가상 인증이다.
4. **기능 범위 문서도 서로 다르다.** MVP 체크리스트는 PRO·에스크로를 제외한다고 쓰지만 현재 화면에는 포함되어 있다. 이 문서만으로 사용자가 제외를 확정했다고 해석하지 않는다. 각 기능의 ‘화면 있음 / 시뮬레이션 / 실제 연동 / 검증 여부’를 다시 표시하는 편이 정확하다.
5. **측정 이벤트와 서비스 동작을 구분해야 한다.** 로컬 재현에서 가상 로그인 후에도 이벤트 `user_id`는 `null`이었다. UI 사용자는 로컬 객체이고 이벤트는 Supabase 세션을 보기 때문이다. 테스트 세션·역할·시나리오·실험 버전이 없으면 사람별 흐름을 연결하기 어렵다. 정상적인 다음 단계 이동도 모달 `close`로 기록되므로 전부 이탈로 집계하면 안 된다.

실제 Supabase 테이블·뷰·RLS 설정은 이번에 확인하지 않았다. 키가 브라우저에 보인다는 사실만으로 비밀키 유출이라고 판단하지 않는다. 현재 코드는 `anon` 키를 사용하며, 실제 운영 전환 시에는 인증된 사용자와 DB 접근 규칙을 별도로 검증해야 한다. 이는 이번 프로토타입 개선의 선행 조건으로 잡지 않는다. [Supabase API 키 안내](https://supabase.com/docs/guides/getting-started/api-keys), [RLS 안내](https://supabase.com/docs/guides/database/postgres/row-level-security)

## 7. 추천 개발 순서 — 제안

1. **연결된 체험 시나리오 만들기:** 사용자 2명, 공고, 보낸/받은 신청, 확정 약속을 연결한다. 자기 신청 수락·잘못된 장소 공개·중복 평가를 바로잡는다.
2. **이동해도 유지되는 흐름 만들기:** 채팅과 약속 상태 유지, 로그인 후 원래 작업 복귀, 완료 후 화면 갱신, 명시적 시연 초기화.
3. **탐색과 화면 완성도 높이기:** 홈의 사용자 상태별 구성, 탐색 명칭, 이벤트 목록·슬라이드, 공통 모달, 본문 안의 고정 버튼, 일관된 날짜·신뢰 정보.
4. **시연과 사용자 테스트 구분하기:** 가상 기능 안내, 연결된 샘플 데이터, 테스트 세션 구분, 성공/실패/빈 상태를 준비한다.

이 순서의 이유는 사용자가 실제로 경험하는 흐름의 모순을 먼저 줄여야 화면의 이해도와 편의성을 제대로 평가할 수 있기 때문이다. 가까운 목표가 정적인 화면 발표라면 3번의 순서를 앞당길 수 있다. 실제 서로 다른 기기에서 신청·수락해야 하는 테스트로 목표가 바뀌면 서버 연동의 우선순위를 다시 판단한다.
